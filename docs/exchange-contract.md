# Future InstrumentHub exchange contract — draft 0.1

This is first-round preparation, **not a supported exchange API or importer/exporter**. CSV reports are not interchange. Each application owns its own database, migrations, backups, accounts, sessions and audit store. No cross-application database reads or writes are permitted by this design. MSTracker owns maintenance execution/detail history; InstrumentHub owns booking/calendar occupancy. A first implementation should be one-way and replay-safe. Two-way ownership, deletion/conflict rules, authentication, transport/TLS and incremental retry behavior need a separately approved design.

## Envelope and identity

A future JSON envelope has `contract_version`, `producer` (name/version), `source_instance_id` (immutable UUID), `exported_at` (UTC ISO-8601 instant), `timezone` (IANA), `correlation_id`, and `records`. Each record has immutable UUID `id`, explicit `entity_type`, `instrument_id`, `revision` (monotonic positive integer), `created_at`, `updated_at`, `change` (`upsert` or future tombstone), `idempotency_key`, and nullable `external_reference`. References use `source_system`, `source_instance_id`, `entity_type`, and `source_record_id`. An explicit instrument mapping is required; names and InstrumentHub numeric IDs are not global identities. Instance IDs survive backup/restore; independent setup produces new IDs.

| Concept | Local storage or future entity | Boundary |
|---|---|---|
| Physical instrument | `instance.instrument_id` | One instrument per database; map explicitly |
| Recurring plan/task definition | `tasks.id` | Category, expected minutes, recurrence, weekday; not execution |
| Dated task occurrence | Future `task_occurrence` | Local due date and state (`scheduled`, `completed`, `skipped`); not a task definition |
| Performed maintenance | `events.id` | Actual UTC instant, original local offset/time zone, author relationship, status |
| Calendar occupancy | Future `calendar_block` | Booking interval, expected minutes, ownership; not execution history |
| Saved follow-up marker | `calendar_markers.id` | Dated marker; is not reserved instrument occupancy or an active notification |
| Outage | Future `outage` | Distinct execution history; never infer outages from missing bookings |

Shareable local records already have UUIDs, creation/update timestamps, revision and optional JSON external reference. Current events are append-only (revision 1). Tasks also use revision 1 because editing is not exposed yet. No speculative occurrence/outage tables exist. Export time must be generated by a future exporter, not copied from fixture data.

## Time, categories and relationships

Use UTC `Z` instants for actual times and provenance, IANA operational zone for interpretation, local `due_date` when calendar semantics require it, and `expected_minutes` for nominal duration. Weekly recurrence is anchored to its weekday; early completion does not shift it. No instrument-usage scheduling in this round. Preserve original offset/fold for ambiguous wall times and reject nonexistent times. Never infer `unplanned` = InstrumentHub `emergency`; retain source category and define a mapping explicitly. Completed and skipped occurrences must remain distinct; a skipped record does not fabricate a performed event. Correlate a performed event to a dated occurrence only when that relationship is explicit.

## Replay, correction and privacy

Idempotency key format in the fixture is `source_instance_id:entity_type:id:revision`. Identical replay is a no-op. Same key with differing payload is a conflict; lower revisions cannot silently overwrite newer records. A future receiver must implement and audit these rules; fixture tests only verify representative data consistency. Corrections/tombstones, including resurrection/conflict policy after restoring an older backup, remain a future design decision. Local restore is recorded in the local audit table.

Exchange/report allowlists must exclude credentials, password hashes, secrets, sessions, CSRF, tokens, private notes and unnecessary contacts. User authentication/identity federation is not part of this contract. The local report CLI exports only event/instrument/task UUIDs, category/status, UTC occurrence/creation and original zone. There is no privileged expanded export policy in this round. SQLite backups are private full-fidelity recovery artifacts, not sanitized exports.

## Synthetic fixtures

`tests/fixtures/exchange-v0.1.json` is hand-authored synthetic data, not lab data or an InstrumentHub export. It covers repeated record identity, completed/skipped occurrences, a performed event across the Chicago DST fall-back, local due dates, expected duration, relationships and secret exclusion. No application code consumes it. Contract checks are preparatory, not interoperability certification.
