## Desired direction and scope

One independently configured instance/database per instrument. Setup captures instrument name/model, IANA operational time zone (default America/Chicago), selected weekly weekday, and first named account. All active users share maintenance privileges; only local CLI/file administrators create, disable, re-enable, or recover accounts. No web administration or special recovery URL.

Include custom routine/unplanned task definitions (name, details, expected minutes, one-time/weekly behavior, optional follow-up), configurable seeded Change ion transfer tube task, routine on-time/early status, persisted future follow-up markers, monthly calendar, paginated basic log, event detail and attribution. Weekly settings use calendar time anchored to the selected weekday; early completion does not shift that anchor. Due-date calculation and instrument-usage schedules are deferred. No correction/delete UI in this round: events remain append-only with immutable creation time and audit history.

Defer search/filtering, outages, background notifications, linked troubleshooting cases/uploads, SST, service visits, manuals, sensitive metadata, due/overdue dashboard, live InstrumentHub exchange, and production installation on an instrument PC. Notes may contain private information and are excluded from default report exports. No deployment/public hosting.

## Implementation approach

1. Write this canonical plan before implementation, keep it unchanged, and create root TASKS.md plus an evolving docs/first-round-record.md containing work/decision/validation records. Suggested commit groups are review aids only; do not stage, commit, push, or invoke a scripted review runtime.
2. Establish a small Python package: app factory in mstracker/__init__.py, explicit transactional SQL migrations and sqlite3 access in db.py/migrations, time validation in timeutils.py, and CLI setup/account/recovery/backup/restore/report commands in cli.py. Use Flask/Werkzeug, Waitress (one worker plus main thread), and bundled tzdata for Windows. Test with pytest. Keep runtime data outside packaged code; reject uninitialized/newer-schema databases and unintended reconfiguration.
3. Store instance/instrument/task/event/calendar-marker UUIDs, UTC creation/update timestamps, operational and original event time-zone/offset context, revision and optional external-reference fields in browsable relational tables. Keep recurring definitions, executed events, and calendar markers distinct. Include a local audit table and session revocation state; do not build unused occurrence/outage tables.
4. Implement password hashes with Werkzeug scrypt; minimum 12-character passwords entered through hidden CLI prompts; generic login errors with bounded retry throttling, CSRF on every form POST, local host restrictions, autoescaped notes, safe headers, HttpOnly/SameSite cookies, 8-hour session lifetime, server-side logout revocation and revocation on disable/reset. No plaintext passwords or secrets in logs. Runtime binds only 127.0.0.1, debug/reloader disabled.
5. Implement server-rendered desktop pages in templates/ and static/: login, calendar, log, task creation/list, new event and event detail. Use Okabe-Ito blue/vermillion tinted entries with distinct icons and text labels, orange follow-up markers, accessible form labels/focus/error/empty states, local assets only. Occurrence defaults to current instrument-local time and is editable when entering an event. Reject future performed times, invalid dates, DST gaps; require earlier/later offset choice for DST overlaps. Calendar placement uses instrument-local date. Transactions prevent partial event/marker/audit writes and form idempotency prevents accidental duplicate submission.
6. Document backup/restore using SQLite backup API, integrity/schema validation, explicit stopped-app restore and session invalidation, fail-on-existing output paths, default CSV secret/private-note exclusion, indefinite history retention and operator-managed backups. Keep migrations atomic and checksummed; preserve existing data and refuse unsupported schema versions.
7. Write a concise versioned future JSON contract and synthetic fixtures covering replay identity, completed/skipped occurrences, DST, category mapping and secret exclusion. Distinguish fixtures/contracts from a shipping importer/exporter. No shared live database or identity assumptions with InstrumentHub.
8. Prepare PyInstaller one-folder bundles for macOS and Windows using a shared build script and packaged install command that copies the bundle to a per-user application directory without overwriting existing installations. Provide a shared auto-start command backed by a macOS LaunchAgent or Windows user Run entry, and documented disable/update procedures. Runtime/setup/recovery must work from the packaged executable. Include a separate reset_admin_password.py entry point for source installations. Test the macOS bundle and installer into a temporary directory, and validate generated auto-start configuration without enabling persistent startup on this user’s computer. Windows build, install, auto-start, offline resource measurement and recovery must be tested on a non-instrument Windows 11 machine before deployment.

Validate synthetic contract fixtures. Run the entire project suite, compile checks, and a local HTTP/browser smoke test if available; inspect final changed/untracked files for scope and secret leakage. Record commands and actual results. Do not count Windows checks, independent reviewer approval, or human acceptance as completed on this host.

## Risks, decisions, and reviewer focus

Local file access remains the trust boundary: administrators can read the SQLite database and reset credentials; backups contain hashes/private notes and require restricted storage. localhost HTTP cookies cannot use Secure; compensate with loopback binding, trusted hosts, CSRF, and SameSite. Check session revocation, DST ambiguity, restore identity and all-or-nothing writes carefully. No data encryption or reminder engine is promised. Windows package/toolchain/resource behavior remains unverified until tested on Windows. User-session auto-start begins at login, not before OS login; enabling it is an explicit local command. Review the minimal schema and provenance contract for future compatibility without assuming live exchange exists. No other agents are used; independent review follows Ariana's handoff.
